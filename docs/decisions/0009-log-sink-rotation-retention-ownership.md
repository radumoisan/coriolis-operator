# 0009: Make Kubernetes Stdout/Stderr The Application Sink And Separate Rotation From Retention

## :material-book-open-page-variant-outline: Context

Milestone 8 delivered the operator-managed per-`CoriolisAppliance` Loki/Alloy stack that collects container stdout/stderr, but the core Coriolis services still rendered `log_dir = /var/log/coriolis` with `use_syslog = yes` and received writable in-container `logs` mounts, while Loki compaction interval and retention delete delay were hardcoded and the only CR tunable was `retentionHours`. Milestone 11 logging hardening (11A) must make the container log pipeline the single application sink, remove the in-container file-logging path, expose the retention pipeline as validated CR settings, and make ownership of node-local rotation versus durable retention explicit. No broader `Ready=True`, HA, production storage, or backup/restore claim is in scope.

## :material-book-open-page-variant-outline: Decision

- **Sink.** Kubernetes stdout/stderr is the application log sink. The Kubernetes-derived `coriolis.conf` renders `debug` from the per-appliance `spec.logging.coriolisDebug` setting (default `true`) and sets `log_dir =` empty, `use_syslog = false`, and `use_stderr = true`, so all core Coriolis services log exclusively to stderr for the container log pipeline and never write in-container log files. The in-container `/var/log/coriolis` log mounts are removed from the core Coriolis workloads; the worker keeps only a dedicated writable `emptyDir` at `/var/log/coriolis/vmware-root` for the VixDiskLib native log path, which is not an application log sink.
- **Rotation.** The kubelet/container runtime owns node-local rotation of container logs. The operator and workloads do not manage rotation.
- **Retention.** Loki owns query retention, compaction, and physical deletion of expired data. `spec.logging` adds optional `compactionIntervalMinutes` (default 15, integer >= 1), `retentionDeleteDelayMinutes` (default 120, integer >= 1), and `coriolisDebug` (default true), rendered into the Loki `compactor` and `limits_config` blocks. The compaction interval may not exceed the retention period (`retentionHours * 60`); the delete delay may exceed retention. Invalid values fail closed into the existing mutation-free `InvalidRuntimeConfiguration` status before any write.
- **Natural-producer evidence contract.** All 14 natural producers of the Alloy application component allowlist (`mariadb`, `rabbitmq`, `keystone`, `barbican-api`, `barbican-worker`, `common-bootstrap-v3`, `coriolis-conductor`, `coriolis-scheduler`, `coriolis-transfer-cron`, `coriolis-minion-manager`, `coriolis-deployer-manager`, `coriolis-worker`, `coriolis-api`, `coriolis-web`) must produce useful records that correlate exactly across the three surfaces: Kubernetes pod logs, Loki, and the adaptor. Memcached is the explicit readiness/readability non-empty-log exception. The logging infrastructure itself (loki, gateway, alloy, adaptor) is self-excluded from correlation but is readiness/readability audited. Synthetic qualification markers remain bounded to the transport/ordering/reconnect/dedup/retention probes and are excluded from natural correlation.

## :material-book-open-page-variant-outline: Consequences

Application log data exists only in the container log pipeline, bounded by node-local rotation, and in Loki, bounded by the CR retention settings; `/logs` and `/log-stream` continue to serve from Loki. `debug` is CR-controlled instead of hardcoded. Removing in-container log files means out-of-stack debugging uses `kubectl logs` and no per-Pod log file survives a container. The retention configuration becomes CR-owned and drift-checked by the spec-derived retention runtime validator. The source implementation and local validation are complete; CIXpress publication and released-artifact runtime qualification, including the new value-silent natural-log correlation validator, remain pending, so this decision is not acceptance or closure of Milestone 11A or broader Milestone 11.

## :material-book-open-page-variant-outline: Runtime Evidence Correction: Coriolis Debug Default Superseded To False (2026-09-08)

The decision text above is preserved unchanged as history. This append-only correction supersedes exactly one element: the `spec.logging.coriolisDebug` default selected in the Decision section (`true`) is superseded by a safe default of `false`.

Released `0.5.56` (source `f0c688bb835b7b80df6e9a803c3acaeda34bdc3b`, CIXpress Default `zom4hw`, CI release commit `6a22a270f312e2f2230829025b56a08e5bdf039f`) shipped the original default `true`. In the isolated `coriolis-m11a-20260908` qualification, the value-silent natural-logs observer's registered-secret hard-fail proved that under `debug=true` the raw value of the retained credential Secret key `temp_keypair_password` (value, hash, and encoded form never recorded) was present in `coriolis-conductor` Pod logs. Source review established that the immutable `2603.4` conductor declares this oslo `StrOpt` without `secret=True`, so Alloy-only redaction cannot make Pod logs safe, and omitting the setting entirely would weaken temp-keypair encryption. The user therefore selected keeping `coriolisDebug` configurable while changing its default and sample to `false`; `true` remains an allowed diagnostic mode but cannot satisfy value-safe acceptance for the immutable `2603.4`. After the target was patched to `debug=false` and normally CR-recreated, the locally corrected observer passed all 14 natural producers value-silently — diagnostic-only, because the default and validator-selector corrections were not yet published at the time of this correction. This correction changes no other element of the decision and is not acceptance or closure of Milestone 11A or broader Milestone 11.
