# Architecture Decisions

Decision records are append-only. New decisions use the next numeric identifier and describe context, decision, and consequences.

Existing records establish the implementation direction for the initial controller.

Decision 0005 accepts CIXpress as CI/release automation while retaining deployment/GitOps as a separate concern. Decision 0006 freezes ingress-nginx as the short-term public-exposure model and keeps TLS Secret material external to the operator. `cr.virtomat.io/virtomat/coriolis/operator` is a provisional repository starting point, not a permanent ADR. Open decisions cover publication/authentication validation and promotion, exact CIXpress repository integration, Argo CRD pre-upgrade automation, and licensing.

Decision 0008 freezes Milestone 9's operator-managed per-`CoriolisAppliance` Barbican (pinned API and worker images only, no listener or PVC, `simple_crypto` with MariaDB-persisted state and a retained ownerless `<appliance>-barbican-credentials` Secret) plus the actual-browser two-endpoint `secret_ref` creation/validation/listing/selection/removal contract with no migration. The architecture is accepted. Release `0.5.52` was published and its first isolated qualification failed before the runtime validator and browser on the API startup configuration defect (WSGI ignored uWSGI `pyargv` and fell back to SQLite); a locally validated startup fix (default-path API config mount, dead `pyargv` removed) passed the corrected local gate. The corrected release `0.5.53` (corrective source `1a0ff21fb74896f76dce879ed021c5cebb20b4ed`, CI release commit `18859efd2e15435448b04e94cc31ba6553bef3ac`, exact isolated operator digest `sha256:418c7036b4f155feb383a2f9771d18846f8a0d35f40d678dfc9de8e7fd3ba767`) then passed isolated deployment, the fixed-output runtime validator, and the actual-browser two-endpoint qualification in `coriolis-barbican-validation-20260906`, and Milestone 9 is accepted and closed for the bounded endpoint credential/browser CRUD scope; the failed `0.5.52` attempt remains preserved history and this is not production qualification.

Decision 0009 accepts the Milestone 11A logging-hardening ownership separation: Kubernetes stdout/stderr is the application sink, the kubelet/container runtime owns node-local log rotation, and Loki owns query retention, compaction, and physical deletion, with validated `spec.logging` settings `compactionIntervalMinutes` (default 15, >= 1, not exceeding retention), `retentionDeleteDelayMinutes` (default 120, >= 1, may exceed retention), and `coriolisDebug` (default false per the 2026-09-08 runtime-evidence correction appended to the record, superseding only the original `true` default after released `0.5.56` proved a `debug=true` Pod-log credential leak), stderr-only core Coriolis service logging with the in-container log mounts removed, and the 14-producer/memcached-exception/logging-infrastructure-audit/bounded-synthetic-marker natural-log correlation evidence contract. Source `f0c688bb835b7b80df6e9a803c3acaeda34bdc3b` was published as `0.5.56` and deployed isolated in `coriolis-m11a-20260908`; the natural-logs observer passed all 14 producers only diagnostically with selector and default-false corrections that are committed and pushed as `dd3530d659896b2ce806920ee6681a65256c82a0` but not yet published (no corresponding CIXpress pipeline discovered in two bounded GET-only observation windows; uncertain non-registration/absence, not a pipeline failure), so corrective publication, released-validator rerun, and formal retention qualification remain pending and this is not acceptance or closure of Milestone 11A or broader Milestone 11.
